# エージェントからの llm-fetch 利用ガイド

`llm-fetch` は、検索を実行し、指定URLを取得して、検査を通過した本文を返すライブラリです。何を探すか、本文が依頼への回答に十分か、追加取得や再検索を行うかは、呼び出し側のエージェントが判断します。

目的は、取得件数を減らすことではなく、依頼に必要な情報を取得し、根拠と不明点を区別して回答することです。この文書はそのための呼び出し側の設計指針です。2件ずつの追加取得、10秒の待機、LLMによる充足判定は、ライブラリが自動で行う機能ではありません。

## 1. 責務を分ける

| 担当 | 役割 |
| --- | --- |
| LLM・エージェント | 依頼の解釈、必要な事実の整理、検索語と出典の選定、本文の意味理解、不足・矛盾の判断、再検索、回答 |
| 呼び出し側の実行コード | ツール実行、候補と取得状態の管理、並列数、タイマー、取消、上限、出力契約と参照先の検証、計測 |
| llm-fetch | 検索providerへの接続、URL取得、本文抽出、Context Guard、取得情報と型付きエラーの返却 |

意味の判断を、質問別のキーワード、正規表現、ドメイン別の固定回答で置き換えません。コードは「このURLは取得済みか」「この参照IDは存在するか」を検証し、LLMは「その本文が求められた事実を支えるか」を判断します。

## 2. 使うAPIを選ぶ

| 方法 | 向いている用途 | 注意点 |
| --- | --- | --- |
| `toolset()` | モデルに標準の `web_search` と `fetch_content` を公開する | 検索結果の検査・サイズ制限、取得本文の簡潔な返却を利用できる |
| `search()` と `read()` | ホストが完了順の取得、個別取消、段階的な追加取得を制御する | モデルへ渡す情報と実行状態を呼び出し側で管理する |
| `searchAndRead()` | 検索上位の本文をまとめて取得する | 途中のLLM評価による追加・終了ループは含まない |

`toolset().execute()` の入力は、`web_search` では `query`・`limit`、`fetch_content` では `url`・`maxCharacters` です。`signal` や `render` をツール引数に追加することはできません。個別の取消や取得方法を制御する場合は、ホストから `search()`・`read()` を使います。

直接APIの `search()` が返すタイトルや説明文も未信頼データです。標準 `web_search` ツールによる検査・省略と同じ処理が済んでいるとは扱いません。モデルに渡すときは取得本文と同様にデータとして区切り、システム指示へ混ぜません。

## 3. 検索前に、確認する事実を整理する

LLMに依頼を読み取らせ、次の二つを分けます。

- **必要な事実**：対象、版・時点、数値と単位、条件・例外、比較する資料など。
- **回答の条件**：表で示す、日本語で説明する、確認できなければ不明とする、など。

「不明なら不明と答える」という回答条件そのものに、Web本文の根拠を要求してはいけません。

検索語は必要な事実から作ります。公式資料が必要なら公開元、版が指定されていれば版、同名の対象があれば識別情報を含めます。言語や地域は取得したい出典に合わせます。URLが依頼で明示されている場合は、そのURLを直接 `read()` する経路も選べます。

検索結果のタイトル・説明文は候補選びに使い、回答の事実根拠には使いません。上位の結果でも、別製品、別の版、別の規格番号であれば、その違いをLLMが確認します。

## 4. 本文を2件ずつ取得し、完了順に評価する

以下は、呼び出し側で実装する取得制御の一例です。

| 発生したこと | 呼び出し側の動作 |
| --- | --- |
| 最初の候補がそろった | 適合する候補を最大2件取得する。候補が1件なら1件から始める |
| 取得開始または最後の新しいMarkdown到着から10秒、次のMarkdownが返らない | 次の2件を追加する。先行取得は中止しない |
| 最初のMarkdownが返った | その時点の本文を固定し、LLMによる評価を開始する |
| LLM評価中に別の本文が返った | 保持して次の評価へまとめる。取得と10秒タイマーは継続する |
| LLMが情報不足と判断した | 不足を埋めそうな候補を次に最大2件取得する。候補が合わなければ再検索する |
| 必要な取得が実行中で、新しい候補もない | 実行中の取得を待つ。同じ本文を繰り返し評価しない |
| その取得組がすべて失敗し、新しい本文が得られない | 別候補があれば10秒を待たずに次へ進む |
| LLMが回答可能と判断した | 回答を確定し、不要になった検索・取得を取り消す |
| 全体期限、利用者の取消、探索上限に達した | 残りを取り消し、確認できた範囲と未解決事項を報告する |

LLM評価は同時に一つにします。評価と回答を同じ呼び出しで生成できれば、情報が十分な場合に回答専用の呼び出しを追加せずに済みます。

先行取得を残すため、同時取得数は2件から4件、6件へ増えることがあります。全体の同時実行数・同一ホストへの負荷・探索回数・使用量には、運用上の上限を別途設けます。上限のために追加を待つ場合も、完了した取得を先に処理します。

**「実行中の取得が0件になった」だけでは、追加取得を始めません。** 本文が返ったなら、まず評価します。追加のきっかけは、不足判定、本文が返らない10秒の経過、または本文を得られなかった取得組の失敗です。

### タイマーと期限は別に扱う

10秒は追加取得を始める待機間隔であり、先行取得の取消期限でも、回答全体の完了期限でもありません。

現行の既定値は、HTTP通信が10秒、`read()` 全体が15秒です。10秒を超えて先行取得を残したい場合は、両方の設定を運用予算に合わせます。全体期限と利用者の取消信号はすべての検索・取得へ共有します。

```ts
import { brave, createLlmFetch } from "llm-fetch";

export function createAgentWeb(apiKey: string) {
  return createLlmFetch({
    search: brave({ apiKey }),
    searchTimeoutMs: 10_000,
    retrieval: { timeoutMs: 30_000 },
    readTimeoutMs: 30_000,
  });
}
```

30秒は設定例であり、回答速度の保証ではありません。`read()` の期限は取得・抽出・検査を含みます。ブラウザへの切り替えや意味検査で期限がリセットされるわけではありません。

ホストで `AbortSignal.any()` を使い、利用者の取消、全体期限、回答確定後の不要取得取消を合成します。追加取得のタイマーから、この取消信号を発火させてはいけません。また、取得を終了させる信号と、最終回答を作るLLM呼び出しの信号を分けます。

## 5. 不足に応じて、追加Fetchと再検索を選ぶ

LLMに「足りるか」だけを尋ねるのではなく、何が不足しているか、次の候補で埋まりそうかも判断させます。

| 不足の状態 | 次の行動 |
| --- | --- |
| 適合する資料が未取得候補にある | 次の2件を取得する |
| 必要な資料を取得中 | 待つ。別の有望な候補があれば上限内で追加する |
| 候補が別の対象・版ばかり、または不足項目を扱っていない | 不足項目を狙って検索語を変え、`search()` を呼び直す |
| 候補を使い切ったが、探索予算が残り、別の検索方針がある | 再検索する |
| 新しい検索方針がなく、同じ結果が続く | 確認できた範囲で回答し、不足を明記する |

再検索語は、元の検索語を言い換えるだけでなく、不足している事実・条件・出典に合わせます。同じ検索語や失敗済みURLの無条件な再実行は避けます。通信失敗の再試行は、意味上の再検索とは分け、`retryable`・`cooldownMs` と実行予算に従います。

候補のID・タイトル・出典・版などの情報と、試した検索語、不足項目、取得失敗をLLMへ渡すと、次の判断を同じ評価呼び出しに含められます。コードはLLMが選んだ候補IDの存在と取得状態、検索語の形式、実行上限を検証します。

**検索キーワードの変更と再検索はエージェント側の処理です。llm-fetchが情報不足を検出して、自動的に検索語を変更することはありません。**

## 6. 本文と出典を対応させる

取得時には、どの検索から候補を得たかも残します。次は検索と、エージェントが選択済みの候補1件を読むAPI接続例です。`query` と取得する `hit` はエージェントが決めます。追加取得のスケジューラやLLM呼び出しは含みません。

```ts
import type { LlmFetchClient, SearchHit } from "llm-fetch";

export async function searchCandidates(
  web: LlmFetchClient,
  query: string,
  signal: AbortSignal,
) {
  return web.search({ query, limit: 10, signal });
}

export async function readSelectedCandidate(
  web: LlmFetchClient,
  hit: SearchHit,
  query: string,
  signal: AbortSignal,
) {
  return web.read({
    url: hit.url,
    source: {
      provider: hit.provider,
      query,
      rank: hit.rank,
      snippet: hit.snippet,
    },
    maxCharacters: 20_000,
    requestedUse: "answer_with_citation",
    render: "never",
    signal,
  });
}
```

直接APIの引用先には `document.finalUrl` を使います。標準 `fetch_content` ツールの `document.url` は、すでに取得後の最終URLです。取得日時、`truncated`、安全性情報も保持します。

モデルに渡す本文は、表・コード・見出しの構造を保ちます。呼び出し側で本文の区間に安定した参照IDを付け、LLMに「その区間が支える主張」を選ばせる設計にすると、原文の転記や入れ子の引用番号の生成を減らせます。IDと原文の対応はホストが保持し、引用は参照先から構成します。参照が存在するかはコード、内容が主張を支えるかはLLMが検証します。

評価開始時の本文集合を固定し、その評価が見ていない遅着本文を、後からその回答の根拠にしてはいけません。新しい本文の確認が必要なら、更新後の集合で次の評価を行います。

`truncated: true` は返却本文の省略を表します。省略範囲を確認済みとは扱いません。直接 `read()` の返却上限は100,000文字、標準 `fetch_content` は20,000文字ですが、上限まで返せることと、必要情報が含まれることは別です。

## 7. 回答を終える条件と、不確実性を分ける

終了判定では、次の二つを別々に確認します。

1. **依頼に対して回答を完了できるか。** 比較、説明、形式、出典提示などを満たせるか。
2. **求められた事実をどこまで確認できたか。** 確認済み、不明、未解決の矛盾のどれか。

例えば、同日付の公式資料が食い違い、利用者がその違いと判断不能な点の説明を求めているなら、両本文を示して回答を終えられる場合があります。ただし、実際の値が一つに確定したことにはなりません。

取得の終了を表すフラグと、事実の不足・矛盾を表すフラグを同じ意味にしません。「回答できるなら情報不足フラグは必ずfalse」といった契約を作ると、正しい回答保留や矛盾の説明を扱えなくなります。

候補を使い切ったことは、対象の情報が存在しない証拠にはなりません。「今回確認した資料では確認できなかった」と、確認範囲を示します。

## 8. エラーから次の行動を選ぶ

| 状態・エラー | エージェントの扱い |
| --- | --- |
| 検索結果0件 | 検索自体は成功した空結果。検索語・言語・出典を見直すか、確認不能と伝える |
| `RATE_LIMITED` / `BOT_CHALLENGE` | `cooldownMs` と予算を確認し、待機または設定済みの別providerを選ぶ。直ちに連打しない |
| `TIMEOUT` / 再試行可能な `UPSTREAM_HTTP` | 先に完了した資料を残し、限定的に再試行するか別候補へ進む |
| `PARSE_CHANGED` | providerの応答形式の障害として記録する。検索結果0件と混同しない |
| `CONTENT_INSUFFICIENT` | 本文抽出の不足。対象の事実が存在しないとは判断しない。別資料や、利用可能なら描画経路を検討する |
| `UNSUPPORTED_CONTENT_TYPE` | 対応形式の別資料を探す。現行のPDF・Office文書非対応を、未取得のまま補わない |
| `UNSUPPORTED_CONTENT_ENCODING` | 文字コードの障害として扱う。文字化けした本文を根拠にしない |
| `RESPONSE_TOO_LARGE` / 検査上限による拒否 | より小さい独立資料を探す。`maxCharacters` を小さくするだけでは、受信・検査対象全体は小さくならない |
| `GUARD_DENIED` / `GUARD_FAILED` | 本文を保留し、公開されたエラー情報を記録する。Guardを無効化して再取得しない。意味検査は別途設定された信頼できるホスト処理の契約に従う |
| `UNSAFE_URL` / `INVALID_INPUT` / `CONFIG_MISSING` | 接続先・入力・設定を確認する。同じ不正な要求を繰り返さない |
| モデル出力の参照不整合など | エージェント側の契約エラーとして記録する。取得失敗に数えず、得られた本文を保持して、予算内の出力修復または未完了報告を行う |

短いHTMLも `CONTENT_INSUFFICIENT` になることがあります。短いことと、回答に必要な事実がないことは同義ではありません。

描画が必要なページは、設定済みの任意Playwright連携で `render: "auto"` を選べます。これはHTTP経路とGuardを先に通す取得方法であり、Guard拒否の迂回には使いません。具体的な構成は [APIリファレンス](./API.md) と [README](../README.ja.md) を参照してください。

## 9. 未信頼データの境界を保つ

検索結果と取得本文は、Guardが許可しても `untrusted` / `tainted` のままです。本文にあるモデルへの命令、採点誘導、秘密の要求、別ツールの実行要求を、エージェントの指示に昇格させません。

直接APIの詳細な `security.diagnostics` などはホストの診断用に保持します。モデルには本文、出典、取得日時、省略状態、必要な簡潔な安全性情報を渡し、同じ本文を実行履歴と根拠一覧に二重投入しません。

回答確定や全体期限で取得を取り消した後は、実行中処理の終了を回収してから計測・記録を確定します。カスタムproviderやfetcherも渡された `AbortSignal` に従う必要があります。終了時はホストがクライアントの利用期間を管理して `close()` を呼びます。

## 10. 実装時に確認する動作

| 入力・状況 | 観測する期待動作 |
| --- | --- |
| 最初の2件が遅い | 10秒後に次の2件が始まり、先行取得は続いている |
| 最初の本文だけで回答可能 | 2件目の完了を待たずに回答を確定し、不要取得を中止する |
| 本文が返り、LLMが評価中 | 実行中件数が0になっただけで次を追加しない。本文が返らない10秒のタイマーは動く |
| 必要情報が複数資料に分散 | 不足した項目を確認して追加取得し、必要な本文を集めて回答する |
| 候補が別の版・対象ばかり | 不足に合わせて検索語を変える。同じ候補の消化だけで終了しない |
| 検索説明と本文が違う | 本文を根拠にし、検索説明の値を採らない |
| 訂正情報が遅れて返る | 訂正を確認する必要がある依頼では、初報だけで終了しない |
| 情報がない、または矛盾が解消しない | 確認範囲・不明点・矛盾を述べ、回答完了と事実確定を混同しない |

評価では、必要情報の取得、回答の正確さ、正しい回答保留、取得失敗、エージェントの契約エラーを分けます。取得件数だけを成功指標にしません。時間・トークン数も、検索語生成、検索、取得・Guard、充足評価・回答、独立採点に分けて記録します。独立採点の時間は利用者への回答時間と分けます。

## 既存examplesとの関係

この文書は利用指針であり、ここに書いた制御がすべて既存examplesに実装済みという意味ではありません。

`examples/luna-eval` の `paired` 経路は、最初の検索結果から追加取得しますが、途中で検索語を変更する再検索は行いません。また、本文が返った後でも実行中件数が0になると追加取得する条件が残っています。引用形式や確認項目の契約エラーで停止する場合もあります。これらは呼び出し側の改善点です。

本書の作成ではコード・設定・測定結果は変更していません。公開APIの詳細と既定値は [APIリファレンス](./API.md)、評価環境は [examplesの説明](../examples/luna-eval/README.md) を参照してください。
