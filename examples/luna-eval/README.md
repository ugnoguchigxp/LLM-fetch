# Luna による検索・取得・回答の評価

利用者のリクエストから、Luna が検索語を選び、llm-fetch で検索し、本文を2件ずつ取得し、Luna が依頼に必要な情報の充足を評価する一連の品質と処理時間を測ります。Codex SDK はこのフォルダの開発用環境にのみインストールされ、llm-fetch 本体の依存や公開APIは変えません。

旧`adaptive`の20件比較では、自動合格率と既知トークンが悪化し、10秒目標も未達でした。現在の既定は、利用者指定の2件ずつ追加する`paired`です。新経路は固定資料3件と取得タイミングを検証済みで、全20件の性能は未計測です。[検証記録](./VALIDATION.md)に原因と全不合格を記載しています。

## 実行

Node.js 22.18 以降と Codex の認証が必要です。既存の Codex ログインの `auth.json` を一時環境にコピーして使用します。ファイルがないキーチェーンのみの認証環境では、SDK/CLIで利用できる認証を別途用意してください。利用者の設定ファイルは書き換えません。

リポジトリのルートで本体の依存を準備し、ビルドします。

```sh
npm ci
npm run build
cd examples/luna-eval
npm ci
npm run typecheck
npm test
npm run list
```

検索には、ルートの `.env` またはこのフォルダの `.env` に `BRAVE_SEARCH_API_KEY` を設定してください。このフォルダの例は [.env.example](./.env.example) です。環境変数が既に設定されている場合はその値を優先します。キーは Codex SDK ではなく llm-fetch の Brave provider が使います。

```sh
# 外部検索を使わず、実際のLunaとllm-fetchで固定資料6件を評価
npm run eval -- --suite fixture

# 全20件: 実サイト14件 + 固定資料6件
npm run eval

# 検索・取得も含めた小規模な疎通
npm run eval -- --ids fetch-http-errors,table-units

# 各シナリオを3回。各評価は現在の根拠だけを渡し、検査と採点も独立
npm run eval -- --repeat 3

# 実サイトだけ、検索providerを変えて比較（DuckDuckGoは実験的）
npm run eval -- --suite live --provider duckduckgo

# 対象や実行予定の確認のみ。モデルも外部検索も呼ばない
npm run eval -- --dry-run

# 採点担当の動作確認。外部検索を使わず、正答・捏造・形式違反を実モデルで検証
npm run calibrate
```

既定モデルは生成・採点とも `gpt-6-luna`、reasoning effort は `low` です。別の Luna が必要なら `--model` と `--judge-model`、または `LUNA_MODEL` と `LUNA_JUDGE_MODEL` で実在するモデル名を明示してください。モデルにアクセスできない場合、他モデルへの自動切り替えは行いません。採点の偏りを点検する際は、利用できる別モデルを `--judge-model` に指定できます。

既定の`paired`は、計画→本文の充足評価と回答→独立採点の経路です。不足時の再評価、Guardの意味判定は追加呼び出しになります。旧経路は`--strategy adaptive`（通常1取得、必要時2並列、最大3取得）、`--strategy search-and-read`（一括取得）、`--strategy staged`（URL選択段階付き）として残しています。20件の評価はモデル利用量と検索API枠を消費します。モデル1回の期限は120秒、シナリオ全体は600秒です。`--timeout-ms`と`--scenario-timeout-ms`で変更できます。

## 評価の流れと境界

1. **計画**: 依頼だけからLunaが必要情報、1〜2検索語、出典ホスト条件を出力。取得の件数や操作はホストが固定します。
2. **最初の2件**: `search()`で各検索最大10候補を取得し、指定された出典条件内の順位順で`read()`を2件開始。別の検索の終了を待たずに取得へ進みます。候補が1件だけなら1件から開始します。検索間の重複URLと取得済みURLは除きます。
3. **10秒で2件追加**: 取得開始または最後のMarkdown到着から10秒間、新しいMarkdownが返らなければ次の2件を追加。先行取得は続けます。追加後も同じ条件で次の2件へ進むため、同時取得が4件、6件以上になることがあります。
4. **最初の本文で評価**: Guardを通過した最初のMarkdownが返った時点でLunaが評価。評価中も取得と10秒タイマーを継続します。評価は同時に1つに限り、その間に届いた本文は次の評価にまとめます。同じ根拠の繰り返し評価はしません。
5. **充足で終了、不足で2件追加**: 必要情報がそろえば同じ呼び出しで引用付き回答を作り、残りの検索・取得を中止。不足なら次の2件を直ちに追加し、先行取得も継続。候補がなければ実行中の取得を待ち、すべて尽きた場合は不明点を明記した回答にします。取得がすべて失敗した場合は10秒を空費せず次の2件へ進みます。
6. **記録と独立採点**: 回答時の根拠を固定し、終了処理を待って計測を確定。独立した呼び出しで目的の情報が得られたかを評価します。

充足の意味判断はLunaが担当します。必要項目ごとに本文URL・短い原文抜粋・その抜粋が支える主張を出し、コードは要件番号の網羅、取得済み本文への抜粋の実在、引用の参照先を検証します。回答の引用は検証済み根拠の番号で指定し、ホストがURLと主張を構成します。文字列があるだけで意味も正しいとみなす仕組みではなく、意味の妥当性は独立採点でも照合します。「未確認」を「不存在」とは扱いません。

`read()`は`render: never`、`requestedUse: answer_with_citation`、最大100,000文字に固定。先頭20,000文字だけで判断していた旧経路から変更し、返却された範囲を評価へ渡します。省略があればその状態も保持します。返却量を制限しても、受信資料全体の既存Guard検査は省略しません。公開元のホスト条件は検査免除には使いません。

10秒は追加取得の待機間隔であり、回答の総時間上限ではありません。新経路は従来の15秒の一括取得期限を使いません。実サイトの通信・取得上限は本体が許容する300秒とし、シナリオ全体の取消信号も共有します。10秒目標の達成は別途`pipelineMs`で測ります。全候補を確認しても情報が不足する場合や、検査拒否・通信障害・全体期限では未解決で終了します。最新の少数試験でも回答は15.61〜21.86秒で、10秒未達です。

生成担当にはシナリオID、期待値、採点基準、referenceUrlsを渡しません。語句一致や質問ごとの専用分岐では採点しません。意味・根拠の妥当性はLLM、コードは形式・出典の存在・上限・停止条件を検証します。Codex は一時ディレクトリで実行し、利用者のMCP・プラグイン・プロジェクト指示を引き継ぎません。独立ブラウズやコマンド等のイベントが出た試行は実行エラーにします。

検索語、取得、回答、根拠との一致、安全性を各0〜4点で評価します。新経路の`goal-v1`は**目的充足、シナリオ別基準すべてpass、回答・根拠・安全性が各3点以上、契約違反なし**で合格です。検索語・取得点数と取得件数は原因分析用で、件数の少なさは合格条件にしません。情報不足を期待する固定資料では、正しい回答保留を対照試験として採点します。旧経路の`dimensions-v1`は全5点数各3点以上を維持します。評価版が違うrunは合格率の単純比較に使えず、比較レポートにも注意を出します。基準の判定unknownや採点障害は `inconclusive`、生成段階の障害は `error` とし、合格に含めません。基準を省略・重複した採点も判定不能です。評価が不合格でも、実行環境の不具合とは限りません。

独立した呼び出しでも同じモデルでの自己採点には偏りがあります。スコアと理由はレビュー補助であり、客観的な正解保証ではありません。シナリオ別の具体的な期待事実を用意していますが、`referenceUrls` は出典案内であり、採点担当が独自にそのURLを再取得する仕組みではありません。実ページの変更で期待値が古くなった場合は、一次資料を確認してシナリオを更新し、以前のrunとは別の評価版として扱ってください。

`npm run calibrate` は採点自体の検証です。出典を提示した正答を合格にし、根拠のない日付と採点誘導を含む回答、および指定の表形式を省略した回答を不合格にすることを確かめます。依頼にない逐語引用を要求しないことと、明示された形式要件を守ることを分けて確認します。期待と異なる採点やモデルエラーがあれば終了コード1です。判定・期待値・トークン・時間・評価コードのhashを `results/calibration-.../` に保存します。

初回の実測結果と、SDKの出力上限および採点指示の曖昧さに関する発見は [VALIDATION.md](./VALIDATION.md) に記録しています。

固定資料のproviderは検索語に関係なく定義済み検索結果を返すreplayです。語句に合わせた検索の模倣はしません。実際のllm-fetchで本文抽出とGuardを通し、検索語・取得先・回答・採点には実際のLunaを使います。**固定資料で実検索のランキングや検索網羅性を測ったとは扱いません**。集計もliveとfixtureを分けます。`npm test` だけはモデル通信を置き換え、契約検証・採点漏れ・使用量集計・Guard等を再現可能に確認します。

## 記録されるもの

既定の保存先は `results/<UTC時刻>-<識別子>/` です。`--out <未使用ディレクトリ>` で変更できます。既存runの上書きは拒否します。

| ファイル | 内容 |
|---|---|
| 各試行のpaired | 各2件の開始時刻と理由、最大同時取得数、最初の本文と評価開始時刻、評価ごとの根拠・抜粋・判断、停止理由 |
| manifest.json | モデル・SDK版、上限、実行日時、Gitのcommit/変更有無、評価コードとビルド済み本体のhash、実行対象と基準 |
| `<scenario>.<repeat>.json` | 検索語、選択理由、全ツール結果・取得本文、回答、引用、各基準の採点理由、段階別計測 |
| results.jsonl | 試行ごとの追記記録。中断後も完了分を保持 |
| summary.json | 全体/live/fixture/シナリオ別集計、段階別時間・使用量、品質分布、失敗コード |
| results.csv | 試行ごとのスコア、時間、生成・採点のトークン、使用量の欠落数 |
| report.md | 合否一覧、回答時間p50/p95、使用量の要約 |

モデル呼び出しごとに入力・キャッシュ入力・キャッシュ書込入力・出力・推論出力トークンを記録します。SDKが報告しない値はnullです。キャッシュ入力は入力の内数、推論出力は出力の内数として扱い、合計は入力+出力です。使用量を返さず失敗した呼び出しは欠落数として残し、0トークンと見なしません。表示される合計は既知分であり、欠落があれば実利用量の下限です。料金は認証方式・契約・価格変更に依存するため推定しません。

`pipelineMs` は検索語生成開始から回答完了までの経過時間（途中で失敗した試行では失敗までの時間）、`totalMs` は独立採点と終了処理も含みます。応答のp50/p95は回答が完成した試行だけを対象にし、早期エラーで応答速度が良く見えないようにします。全試行の時間は `attemptMs` に別集計します。各段階にSDK起動・ネットワーク・構造化出力処理の時間を含みます。`firstEventMs` と `firstMessageEventMs` はSDKイベントの観測時間です。**SDKはトークン単位の差分を公開しないため、厳密なTTFTや生成tokens/secondは計測していません**。少数標本のp95は参考値です。

文書キャッシュは無効、シナリオ間の試行は直列です。`paired`の各充足評価は現在の根拠だけを渡す独立会話とし、履歴と同じ本文を二重に送らないようにしています。旧`adaptive`の計画と回答・追加判断はシナリオ内の同じ会話を使います。検査・採点・次のシナリオは独立会話です。provider側の状態やモデルのprompt cacheまでリセットするものではありません。反復比較は同じモデル・SDK・provider・シナリオhash・本体ビルドで行い、生成と採点の使用量を分けて比較してください。

全件合格時は終了コード0、不合格・判定不能・実行エラー・未完走は1です。Ctrl-Cでは進行中の呼び出しをキャンセルし、完了分と不完全なrunを保存します。同じ実行エラーが3回続いた場合は自動再試行せず停止します。結果を捨てて合格するまで再試行する処理はなく、予算内の追加調査も1試行に含めます。`--repeat` の結果はすべて分母に含まれます。

保存先はGit除外・ディレクトリ0700・ファイル0600です。本文・依頼・回答を含むため、外部共有の前に内容を確認してください。生成した証跡は公開パッケージには入りません。

## シナリオの追加

[scenarios.ts](./scenarios.ts) に依頼、分類、具体的な判定基準、一次資料URLを追加します。固有の語句に反応する製品コードや評価コードは追加しません。別のJSON配列を `--scenarios <path>` で指定することもできます。形式はmanifestのscenariosを参照してください。fixtureを指定する場合は [fixtures.ts](./fixtures.ts) に資料セットを用意します。

## 設計・検証範囲

本体のHTTP取得・公開ツール・Guardは既存実装を再利用しています。Playwrightによる描画、Wikipedia専用adapter、Guard上限・本体APIの変更は含めていません。追加取得はLunaの不足判定または10秒の待機条件で、検索候補と上記の期限内だけで実行します。動的サイト等で本文が取得できない場合も失敗として記録し、評価のために本体の制約は緩めません。

公式仕様: [Codex SDK](https://developers.openai.com/codex/sdk/)、[Lunaを含むモデル案内](https://learn.chatgpt.com/docs/models#recommended-models)。

## 保存済みrunとの比較

```sh
npm run eval -- --strategy adaptive --service-tier fast --out results/my-adaptive-run
npm run compare -- --baseline results/2026-10-16T06-01-57.485Z-5cdad97a --candidate results/my-adaptive-run
```

比較は同じシナリオ・反復集合を必須とし、モデル・SDK・tier・シナリオ・本体ビルドの一致、評価コードの変更も記録します。`comparison.md`と`comparison.json`に全体・実サイト・固定資料、取得試行/成功/中止、生成/採点の既知トークンと欠測数、p50/p95、10秒以内かつ合格の件数を保存します。計画と回答のモデル時間だけで10秒を超えた件数も分離します。
